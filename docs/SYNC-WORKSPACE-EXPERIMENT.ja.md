# Folioの端末同期実験

Level 3 のローカル運用を既定にする。同期を試すときは専用の `FOLIO_DATA_DIR` と `FOLIO_SYNC_ENABLED=1` を指定する。実端末2台での同期と復旧の確認後に Level 4 を判定する。

## 保存から適用まで

SQLite の内容変更と同じトランザクションで送信待ちの世代を記録する。送信前にワークスペースのスナップショット、基準リビジョン、操作IDを確定する。ACK が失われた場合は操作IDで結果を照合し、未確定なら同じ送信内容を使う。受信キューと受信位置、ローカルの置換と適用位置は、それぞれ同一トランザクションで確定する。

本文、ブロックID、階層、DB定義・ビュー、recordと所属・値、履歴、添付台帳、ゴミ箱の削除時刻と復元関係を同期する。検索用の列は受信した本文から再計算する。端末の表示設定、保存レシート、クラッシュ復旧記録、端末バインディングとトークンは端末側に置く。

競合はワークスペース単位で扱う。独立したページの編集同士でも、同じリビジョンを基準にした場合は競合する。ローカル候補とリモート候補を永続化する。ローカルを選ぶ場合は観測したリモート版を基準に新しい操作を送る。リモートで増えたページや添付を候補から落とす選択は拒否する。リモートを選ぶ場合は適用直前のローカル内容も保全する。

添付はワークスペースに分離した SHA-256 の経路で転送し、検証済みのファイルを確定してから本文と台帳を適用する。アップロードは最大 1 MiB のチャンクを再送できる。ダウンロードの通信中断は同じ実行内で受信済みバイトから再開する。プロセス再起動後は、完了済みファイルを再検証して再利用し、途中のファイルは転送し直す。

## 起動・復元

現在の実験では、同一プロファイルの単一起動を取得した main が、編集画面を作る前に同期する。画面を閉じて起動し直すと、その間の保存が次の同期対象になる。入力途中の値、未確定の操作、読めない復旧記録が残っているときは適用を保留する。起動時の同期結果は保存状態と別に表示する。

初回の公開側に `FOLIO_SYNC_MODE=publish`、空の参加側に `FOLIO_SYNC_MODE=join` を指定する。2回目以降はモードの指定を省略できる。移行前に完全バックアップを検証し、同期用テーブルと SQLite v5 を同じトランザクションで確定する。v4 以前の Store は v5 を開けず、移行前から開いていた接続の製品データ書込みも拒否される。

完全バックアップの復元先はローカルで開ける。同期へ戻すときはサーバーに新しい端末IDを登録し、新しいバインディングで `FOLIO_SYNC_MODE=recover` を明示する。復元先の旧キューは再登録前の完全バックアップへ退避する。新しい候補は既存リモートの内容と競合として比較できる。

起動時の環境変数は `FOLIO_SYNC_URL`、`FOLIO_SYNC_WORKSPACE`、`FOLIO_SYNC_CLIENT`、`FOLIO_SYNC_BINDING`、`FOLIO_SYNC_TOKEN`。バインディングは端末ごとに生成する。競合の明示選択には `FOLIO_SYNC_CONFLICT_CHOICE=local` または `remote` と、観測した `FOLIO_SYNC_CONFLICT_REVISION` をその起動だけに指定する。

## 検証

```sh
npx vitest run tests/sync-level4.test.ts tests/sync-level4-transport.test.ts --maxWorkers=2
npx vitest run tests/sync-workspace-startup.test.ts tests/sync-workspace-store.test.ts --maxWorkers=2
npm run verify:quiet
```

テストは Node の独立プロセス、使い捨て SQLite、試験専用の loopback HTTP を使う。専用の中継プロセスで通信断、サーバーが確定した後の ACK 喪失、受信順序の逆転を作る。強制終了の対象はテストが起動した子プロセスに限る。

実端末の試験では隔離したサーバーと、各端末に別々のデータフォルダーを用意する。サーバーは `127.0.0.1` で起動し、2台目は認証済みのトンネルで自端末の loopback に接続する。端末登録は `startCheckpointServer` の `registerDevice` をサーバーホストから実行する。両方向の再open、切断と再接続、競合選択、削除と復元、復元先の再登録を確認する。Windows を使う場合は Windows 上のビルド、添付の確定、復元を加える。GUI 検証は明示指示を受けた回の `npm run test:e2e:batch` を使う。

## 実験の上限

チェックポイントは 1 MiB、添付1点は 20,000,000 バイト、受信は1回1リビジョン。起動時の受信回数にも上限を置く。サーバー・端末の同期履歴と適用前バックアップは保存を続ける。ディスク容量と、履歴が大きくなったワークスペースの転送コストを考慮して試験データを選ぶ。サーバーと添付ディレクトリには単一の所有プロセスを使う。サーバーDBを過去へ復旧するときは新しい epoch で再登録する。
