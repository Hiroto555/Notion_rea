# R5 A1 — database operations and owner sessions

## Implemented contracts

`shared/database-operation.ts` defines `DatabaseOperation` and `DatabaseOperationResult`.

- `prepareDatabaseCreation(title, parentId = null, settings?)` synchronously creates one stable operation. The caller retains it until a terminal response.
- `database:commit` and `database:resolve` take `{ operation }`. Operation identity is `(operationId, sessionId, seq, command)`; SHA-256 uses the same canonical JSON as the R4 receipt layer.
- Commands: `createDatabase`, `createRecord`, `updateDatabase`. The latter atomically saves owner Page metadata/body and database settings using one owner revision and history entry.
- `database:read` returns `{ page, database }` from one `Store.load()` snapshot.
- `renderer/reliable-database-operation.ts`: `sendDatabaseOperation` and `resolveDatabaseOperation`, default 15-second timeout. Timeout, transport rejection and ACK mismatch are unknown. No automatic retry.

All commands share R4's `save_receipts` operation-ID namespace. Equal ID/content returns the original result without a second mutation; different content with the same ID is rejected. Receipt absence stays unknown. The applied receipt and mutation commit together. Business rejection is recorded only after rollback to the operation savepoint; failed transaction cleanup poisons Store and prevents even receipt reads through its guarded `db` accessor.

Creation results return the actual created Page, record (for row creation), and database projection. Record creation checks the owner revision and current property schema inside the write transaction. It creates record revision 0 and leaves owner revision unchanged. It does not need to rewrite other records. A view/owner update increments the owner once. R5 refuses deletion or mutation of existing property definitions on this new settings path; adding a property is supported by the existing semantic intent.

## Session ownership

`DatabaseSessionCoordinator` belongs to App, independent of mounted database views:

- `attach(page, projection)` returns `{pageId, sessionId}` and does not replace an existing lane from refresh.
- `editPage`, `editSettings(SettingsIntent)`, `createRecord` retain ordered intents and return their sequence. They do not start saving.
- `get`, `views`, `subscribe` provide display overlays and saved/pending/saving/conflict/unknown state.
- `flush` serializes owner metadata, settings and record creation; `resolve` queries the exact unresolved operation and only then resumes later intents.
- `lastResult` retains the latest applied record creation with its sequence across later settings ACKs. The full projection contains all created records.
- `hasUnsaved` covers queued intents, in-flight requests and unresolved results; App uses it for normal exit/reload protection.

Semantic settings application reuses `applySettingsIntent` and canonicalization. ACK installation reuses existing owner-Page validation and transition comparison, so a settings-only response cannot silently introduce a different owner body. A receipt can describe an older successful state than a current external read; this does not authorize rebasing. A subsequent write uses the acknowledged revision and conflicts against any newer external owner revision.

## Explicit v3 → v4 boundary

Only the new explicit `createDatabase` command enables the record schema in a v3 workspace. Before the transaction it writes a non-overwriting, unique SQLite snapshot named `workspace.sqlite.pre-r5-records-<uuid>.sqlite`. Then one transaction creates/validates record schema, sets the v4 marker, inserts/registers the new owner and writes its receipt. Failure rolls back the schema/marker/owner with the mutation. Existing legacy DB Page JSON/rows are neither registered nor converted.

The snapshot contains SQLite only. Attachments are unchanged by these operations, but it is not a complete workspace backup. There is no await between the main-process snapshot and transaction, but arbitrary external writers are not excluded; the snapshot is not claimed to be an exact cross-process/cross-file preimage. Partial snapshot files after failure are retained and never reused. Existing startup v1/v2→v3 migrations remain unchanged. Existing generic `Store.create(database)` behavior also remains: once a workspace is v4, that existing route registers newly created DBs.

## Validation and limits

A0 reported check PASS and focused unit 18/18 (14 new core cases + 4 view cases) after syntax correction `6cf640d`. A first check failed because of a newline before a TypeScript `as` assertion; that was fixed without changing assertions. Follow-up `b0b5fe4` adds one ACK-body-corruption test and strengthens snapshot checks; its rerun remains A0-managed.

Tests cover v3 snapshot/legacy preservation, lost creation ACK and reopen, duplicate/different-ID-content behavior, receipt failure rolling back DDL/data, owner/schema conflicts, unified owner/settings revision/history, shared R4 collision protection, poisoned rollback, revision limit, delayed ACK, navigation-independent drafts, settings/create ordering, no resend on absent receipt and external owner conflicts.

Drafts and unresolved operation identities remain in memory. Receipts persist, but there is no durable outbox or automatic crash recovery. App must block normal exit/reload while input is unresolved. Existing arbitrary-writer exclusion, owner ABA, full backup/restore and receipt retention/compaction remain outside this round. Date properties retain the existing string-value contract; R5 UI targets text, number and checkbox.
