# R6 A1: 強制終了後の入力復旧

担当worktree: `<workspace-root>/Folio-r6-20261028/recovery`、branch `codex/r6-recovery`。R5 `ac1d2ad` を起点とし、元repo、R5、実利用データへ書込みなし。push、master mergeなし。

## 実装

- `shared/crash-recovery.ts`: schemaVersion 1の限定snapshot。通常Page、record、DB owner/settings/行作成の入力世代とbase、未確定operation、DB作成、構造変更operation、未完成数値文字列を保持。32 MiB、深さ120、50万node等を制限。重複lane/operation/rawキー、順序不正、要求と入力内容の相違、非JSON/循環を拒否する。構造変更operationは保管のみで、実行側がfamily固有schemaを適用する。
- `persistence/crash-recovery-file.ts`: SQLite settings内のworkspace UUIDとjournalを結合。checksummed canonical JSON、generation CAS、staging file fsync→同directory rename→readback→file/directory fsync後にACK。同generation同内容は失われたjournal ACKを二重世代更新せず回復できる。壊れた/foreign/未知schema/oversize journalは上書きせずblocked。失敗したstagingは保全する。空snapshotも新世代で保存し、未処理journalの削除はしない。
- 両session coordinator: `beforeSend`はoperation ID確定・通知後、IPC送信前にawaitする。`exportRecovery(includeClean=false)`はPromiseを除いてbase/intents/session/seq/operationをコピー。`restoreRecovery(entry,current,resolved?)`は既存laneを置換せず、明示的startup actionとしてのみ使う。
- `renderer/crash-recovery-resume.ts`: receipt照会appliedならoperation.seq以下だけ除去。fresh sourceがreceipt後の本文/recordと一致した時だけ後続inputを復帰。外部変更は拒否し、原本を変更しない。absent receiptはunknownを保持し、flushは再送しない。DBはowner Page/settingsを完全比較し、他のrecordへの無関係な更新でownerをrebaseしない。
- `persistence/crash-recovery-copy.ts`: 明示的fallback。別の通常Pageへ本文と全payloadのJSON code blockを保全。recoveryIdと内容fingerprintのdeduplication receiptをPageと同一transactionで保存し、ACK喪失後も同じIDの再照会相当の呼出しは二重作成しない。元Pageの変更、record membership/schemaの移動、保存要求の実行は行わない。
- `renderer/recovery-checkpoint.ts`: 入力callbackで即時cloneし、未送信snapshotだけをcoalesceするrenderer queue。同内容のofferは通知・書込みを増やさない。flushは呼出時の入力世代までdurable ACKを待つ。timeout/IO/CAS/不正ACKはerrorを保持し、明示retryは失敗した同generation・同snapshotから再開する。application operationの再送は行わない。
- `unverifiedInputs`: stale editor callback、不明provenance、未登録sessionなどを元の入力のまま保管するcopy-only欄。通常Pageの現在baseに結合し直さない。A0のstartup判定はこの欄があれば原本へのresumeを拒否する。

## A0接続契約

1. startupで`crashRecoveryWorkspaceId(store)`と`new CrashRecoveryFile(path,id).read()`。blockedは上書き禁止、readyに入力があれば明示的復旧UIを出す。
2. 全入力・ACK変化のcallbackで同期capture→serialized persistence queue。各送信前はoperationをsnapshotへ含めてqueue barrierのACKを待つ。通常Page、新DB作成、migration/propertyも同じ境界が必要。
3. 未確定operationは`resolveReliableSave`/`resolveDatabaseOperation`等の検証済み照会だけを使い、その後fresh readを行う。reconcileまたはrestore APIへ渡す。
4. raw数値文字列は対応laneを`includeClean=true`で同時保存し、そのlaneのbase検証成功後だけ復帰。conflictのraw値もcopy payloadに残す。
5. 復旧受理・copyのACKまで元journalを保持し、全項目を扱ってから新snapshotをdurableにする。復旧途中のfailureで未処理項目を落とさない。

## 限界

- 入力のdurable ACKより前にSIGKILLした文字は保証しない。UIはcheckpoint保存中/保存済みを区別する。
- atomic rename/fsync成功は、すべてのfilesystem/deviceの突然の電源断保証ではない。添付・完全workspace backupではない。
- 1つのmain processがjournalを所有する。任意の外部writerや悪意あるdirectory置換との一般的排他は対象外。
- 破損/foreign journalは保全・blockedとし、自動的な消去や修復はしない。
- 実SIGKILL/Electron再起動の統合証拠はA0実行分。unitのcoordinator再生成をその代替証拠にしない。
