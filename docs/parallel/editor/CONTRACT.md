# Editor 2.0 文書 ID 契約と統合上の注意

基準は `b7c150d15739c59edf6ba9a62ebda4794748d46b`。このbranchは `src/shared/types.ts`、`src/persistence/store.ts`、`src/renderer/App.tsx` を変更しない。

- IDは文書内のブロックと構造コンテナごとに持つ `attrs.id`。生成値はUUID、重複しない範囲は**同一文書内**。ページ複製・退避から作った別ページと元ページの間で同じIDが存在しても、それぞれ別の文書として扱う。世界全体で一意とは主張しない。
- IDのない旧文書は従来どおり読める。Editor内では表示時にIDを補うが、その操作だけではDBへ書き込まない。初回の実編集時、従来のpending edit・revision・保存経路を通って文書とIDが一緒に保存される。保存に失敗した変更は既存の退避経路を使う。編集・保存前に閉じた場合、次の表示時に生成し直されるため、未保存のIDは永続IDではない。
- 移動とUndo/Redoは既存IDを維持。複製、HTMLの貼付け、コピーとしてのドロップは新規IDを発行する。現時点の貼付けは切取りかコピーかを識別しないため、切取り→貼付けでも新IDとなる。切取り移動のID維持は未実装。入力ドキュメントでの空・過長・重複IDは拒否し、未知属性・未知schemaの原文保護を維持する。
- 入力schemaは引き続き `schemaVersion: 1`。旧データを新コードが読む互換性を検証する。一方、共通基準 `b7c150d` のvalidatorを実際に組み立てて検証した結果、IDのない文書を受け入れ、ID付き文書を拒否した。旧版アプリ全体の復旧・読込挙動までは未検証であり、旧版による編集互換を保証しない。共有schema/DB側で正式な移行versionや後方互換策が必要なら、統合前にDatabase担当と調整する。
- 最大サイズを増やしたり内容を切り捨てたりしない。IDを付けるとデータサイズが増えるため、上限近傍の旧文書への初回編集が拒否され得る。既存のpending edit/退避が保持されることと、実サイズの境界を別途確認する必要がある。
- ネスト操作は既存の位置で子を複製・削除・順序変更でき、ドラッグは妥当な構造で別の親へも移動できる。自身や子孫への循環を拒否し、移動後のProseMirror schemaを検査して不正構造の書込みを拒否する。最後の子の削除など構造を壊す操作は拒否する。ネストしたリスト項目の先頭段落は親ハンドルとの重なりを避け、カーソルからの選択操作を提供する。
- 新しい永続ID属性をリッチHTMLに出力する。貼り付け時は読み込んだIDを新規に付け替える。既存E2EでOSクリップボードを使用する一般的なHTML貼付けは通過した。ID付きブロックのOSクリップボード経由の複製、他製品との相互運用、添付の全形式や100,000ノード規模の性能は未確認。
