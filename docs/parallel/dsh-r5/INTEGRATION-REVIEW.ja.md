# Folio Round 5 integration review

2026-11-05。Round 4の `5a10ede` を基準に、GUIを使わずに起動前・移行・単独救出の残件を実装し、GitHub反映用に統合した。

## 実装と確認した経路

| 対象 | 変更・検証 |
| --- | --- |
| 起動前の容量確認 | 書込み用SQLiteを開く前に、旧スキーマの移行前コピーに必要な容量を確認。未対応の将来版はジャーナル設定を書き換える前に拒否する |
| 移行前の退避 | 新しいコピーを作成・検証・fsyncし、既存の退避ファイルを上書きせず公開。途中ファイルが同じ名前で残っていても流用しない |
| 読み取り専用の起動 | 容量が確保できない対応DBを、初期化やseedを行わずに開く。保存済みページの閲覧と原本書き出しを提供し、main側でも保存・復旧checkpointを拒否する |
| 旧ワークスペースの取込み | 保持する退避と公開する作業コピーの両方を見積もり、作成前に容量を確認。DBと添付を検証し、未完了マーカーとディレクトリのdurability barrierを使用 |
| 単独救出 | `npm run folio:rescue` とビルド済み `dist/raw-rescue.cjs` を追加。起動に失敗する旧スキーマや壊れたPageを、移行せずに読み取り専用で救出する |
| オフライン検証 | 通常のNode通信APIを子プロセス内で拒否し、別プロセスで同じ操作を保存・検索・照合・再open・ローカル書出し。TCP/fetch拒否も実行確認 |
| 配布ファイルの検査 | HTMLとCSSが参照するスクリプト・スタイル・フォント等がローカルに存在することを、ビルド後に検査。GitHub CIでも同じ確認を実行 |

通信禁止の試験はNodeのAPIを対象にする。OS全体のネットワーク遮断や、Electronの実画面での操作は後続のGUI確認で扱う。

## 分担とレビュー

DeepSeek Harness headless / Flash 4.1 / reasoning maxの4担当を、独立worktreeで実行した。Aはスキーマ起動保護、Bは旧保存先の取込み、Cは通信禁止下のライフサイクル試験、Dは単独救出CLI。Cの初回は応答が止まったため、その作業専用プロセスだけを終了し、新しいheadlessセッションで再開した。完了HEADと各ログはローカル成果物の `RESULT.json` に記録した。

Codexが接続・レビュー・統合を担当し、次の問題を独立再現して修正した。

- 正常な起動前検査で読み取り接続が閉じられず、繰返し時に接続が残った。成功時にも確実に閉じるようにした。
- 読み取り専用接続の `query_only` が外部スナップショットの作成も拒否した。呼出し元の保護を維持し、外部コピーに専用の読み取り接続を使用した。
- インポートと救出の後処理が、他の読取り接続の使用中のSQLite共有ファイルを削除し得た。SQLite自身に寿命管理を任せ、コミット済みのDB/WALの保持を検証した。
- WALモードの読取り開始で生成される空のWALをデータ変更と誤認した。内容のないWALと未作成状態を同じ論理状態として扱い、実データや添付・ジャーナルの変化は引き続き拒否する。

## 判定と境界

Level 2到達、Level 3部分達成。今回、固定したLevel 3基準に関係する起動前・単独救出の実装と非GUI証拠を追加した。G1/G8の製品画面でのネットワーク遮断下の起動→編集→保存→再open、容量停止からの操作、IME、フォルダー選択はNOT_RUN。GUIの確認対象は `docs/GUI-VALIDATION-QUEUE.ja.md` に記録した。

同じボリューム内の退避、DB容量の事前判定、未知の添付参照の保全などRound 4の運用条件を継承する。SQLiteの読取りで共有メモリーインデックスや空WALが生成・更新されることがある。単独救出は利用者によるアプリ終了確認と変更検出を組み合わせ、外部プロセスの完全な排除まで保証するものではない。
