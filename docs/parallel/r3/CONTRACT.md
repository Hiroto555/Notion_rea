# Round 3 shared contract

Status: this document describes the intended interface and behavior; it does not assert that Database 3 is ready for use. The current App preview described here is an uncommitted integration-worktree candidate and is not present in the committed branch by itself. The base is the fetched master. Existing SQLite v3, DatabaseData v2, Page/Doc v1 and recovery v2 remain in production until an independently tested migration changes them. Core provides experimental record, database settings and read IPC; the record-save Coordinator and DatabasePresentation are not connected to App. App excludes identified records from the normal tree and can show a record reached through search or a link as a text-only, read-only body preview. The preview does not provide the required full-page Editor or preserve rich presentation. Automatic migration and live DB UI composition are unavailable. DB UI fixtures do not establish live persistence.

The preview disables the record title and several direct edit controls, but it is not a blanket read-only mode for all record actions. Generic lifecycle and history actions remain exposed and their owner/provenance protections are incomplete; other controls may still attempt an update. Do not infer that these actions are safe or disabled from the preview label.

## Identity, ownership and presentation

A record is intended to be a Page: pageId identifies the document, title, icon, revision, deletion state and history. Block identity is scoped to the document and external references are (pageId, blockId). The intended Editor receives documentId=pageId and is keyed by pageId; App owns navigation, PendingEdits, errors and recovery. Full-page record editing is required; peek is not adopted in this round. This Editor connection is not currently implemented: the record body uses the text-only preview described above. DB membership is separate from parentId; a record has one databasePageId and is hidden from the normal page tree, yet can be opened by search or links. Moving normal page hierarchy must not silently change membership. The intended lifecycle prevents independent restoration while the owning DB is trashed, preserves independently trashed records on DB trash/restore, and creates independent identities when duplicating. Direct record lifecycle and generic actions still need the owner and provenance safeguards described below.

A live owning database's `DatabaseProjection.records` includes both active and independently trashed records, with their canonical `deletedAt` and current revision. Normal table/board/calendar/gallery views filter to `deletedAt === null`; a restore surface may show independently trashed records. `database:load` rejects a trashed owning database, rather than presenting batch-trashed records as independently restorable. Restore the owner through the database lifecycle first; after restoration, individually trashed records remain trashed. `record:get` is a separate read-only projection and does not by itself establish that the owner is active.

`DatabasePresentationProps` in shared/types.ts fixes the owning `databasePageId`, a read-only projection and named async callbacks. Core must supply that ID even when there are no records, so scroll/focus state cannot be shared accidentally between empty databases. `RecordProjection.pageId` is never a legacy row id. `DatabaseProjection.settings` contains properties, views and active view but no rows. Legacy model helpers can use local derived v2-shaped copies for filtering/sorting only; they must not be passed to a save callback. UI owns controls; Core owns composing the record page and Editor, and passes display-only UI props/slots after agreed extraction. The intended integration has no separate autosave queue. It must surface callback failures without silently discarding input; this has not been established in the live App. Opening a filtered-out record must not close it; navigation should return to the owning DB where possible.

## Writes, concurrency and IPC

`record:patch` now requires `{ type: "record:patch", pageId, databasePageId, revision, patch }`: the caller supplies the observed owning database ID. Storage checks that exact membership, a live registered understood owner, the live Page, schema and revision inside the write transaction before changing title or values. A record revision must be safely incrementable; an increment beyond `Number.MAX_SAFE_INTEGER` is rejected without writing. A missing owner is invalid at IPC validation. This is a wire change: callers and fixtures must supply the owner.

For an owner-bound Coordinator lane, the record ACK must match the complete trusted projection after applying the exact title and per-key value patch, including untouched fields, before the corresponding pending entry is acknowledged. A Page ACK currently invalidates that trusted record projection; subsequent record writes stop with their drafts retained. The current resync API refuses pending or failed edits, so it cannot re-establish the base while preserving those drafts. A safe resynchronization and recovery path remains to be implemented. Unbound Coordinator mode is a prototype and is not sufficient for App integration. An owner ID and revision alone do not prove the absence of an A→B→A membership change; an ownership generation and old-binary exclusion remain unresolved. Direct record lifecycle and generic record history operations also require separate owner/provenance work. This record patch foundation is not connected to App's editing flow; the preview does not disable every generic action.

`RecordRequest` declares the planned command names and fields. Page record title/doc/icon and membership values share one Page revision. Property `values` is a per-key patch (null deletes a key); title and doc use the same optimistic revision. A `record:patch` ACK is a projection, never a doc snapshot. The intended App integration serializes edits through one queue and preserves and reapplies pending changes after each verified ACK; this integration is not present. Stale revisions must reject without writing. The Coordinator retains failed drafts in memory, but a general safe retry or export for record drafts, including externally conflicted drafts, is not currently available in App; existing recovery guards refuse some unsafe Page-only exports. Database settings have their own owning database Page revision; `database:settings` validates settings and rejects rows. The intended lifecycle uses atomic transactions and rejects stale or unsupported inputs, but the generic lifecycle and history routes still need the ownership and provenance work above. `record:create` ACK returns a projection; trash returns void; restore/duplicate return projections. IPC validation must be strict, enforce current size limits and reject unsupported fields. `record:read` returns a full Page and matching record projection from one SQLite read transaction for a live, understood record and registered live owner. Before using its revision for an Editor, App must install both the Page and actual Editor document; this integration is not present. The record schema is not automatically enabled.

## Migration, history and compatibility

The migration must use a persisted mapping keyed by (databasePageId, legacyRowId), not legacyRowId alone; generate collision-safe page IDs and reuse the mapping on retries. Before changing the version, it must capture SQLite and matching assets under verified exclusive workspace and asset ownership. Known forms and the SQLite user_version bump must be converted atomically, with interruption and rollback failures handled safely. Current snapshot and conversion helpers do not enforce that ownership, provide a complete crash journal, or enable live migration. Preserve unknown/malformed page, document, database and history bytes, and refuse unsafe writes. Historical legacy DB snapshots must remain immutable; restoring a known snapshot must reconcile title/values/membership through the mapping while preserving post-migration document bodies and existing newer records. Unknown history must stop without changes. DB settings history and record page history are distinct. The new SQLite version must cause the tested old binary to reject it, but a version marker alone does not exclude every older process or protect assets. Backup and recovery must include membership, property values and referenced attachments; version formats independently and test isolated restores. No live-data downgrade.

## Boundaries and integration

Core owns shared types/validation/recovery, persistence, main/preload, App, pending-edits, database/model, launcher, dependencies and shared fixtures. Editor owns src/editor, editor-only CSS/tests. DB UI owns Database.tsx, FilterBuilder.tsx, new database display components and dedicated CSS/tests. Fidelity owns Modal.tsx, shared styles.css, agreed display-only extracted components, comparison and fidelity tests. The shared contract commit touches Editor only to introduce documentId; subsequent Editor work owns it. UI needs Core extraction via a change request, not edits to App. Dedicated tests belong to their lane; existing shared tests require written rationale and Core review, no weakening/skip. Contract changes are requested to Core with consumer, example and tests; Core publishes a follow-up contract before dependent integration. Integrate Core → DB UI → Editor → Fidelity after inspecting each branch. Lane-specific AGENT_TASK.md and folio-agent.json are setup-only commits, never blindly merged.

## Integration worktree continuation

The uncommitted integration candidate can render the DB UI in a separate read-only component. Its view/month selection is local only; it mounts no editing writer or form drafts. A record open is re-read and owner-checked before navigation, and outdated opens are ignored. The record preview is still text-only. Registered DB and record lifecycle controls are disabled in this candidate, but generic IPC, stale search/link classification, concurrent old writers and physical IME are not proven safe. This is not the required editable Database 3 integration.

`folio-pending-journal` version 1 is a manual inspection record of captured pending generations, not an automatic recovery file or complete backup. The recording operation does not acknowledge, apply or discard pending input; it records only the snapshot taken before the dialog, excludes assets/history and refuses malformed or excessive content. Input captured after the dialog begins is not included. Unknown or oversized pending shapes may prevent export while remaining in memory. Successful publication retains a mode-0600 hidden staging hard link beside the destination; a failure after publication may leave the destination and/or staging file, and neither should be automatically overwritten or removed. The writing helper requires exclusion of concurrent directory mutation and does not establish crash durability on every filesystem. On an unknown record/Page conflict, the candidate does not blindly retry unproven drafts against a newer revision.
