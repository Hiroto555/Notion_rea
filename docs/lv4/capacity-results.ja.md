# 合成workspaceの容量計測（途中）

2026-11-07、Node 24.20.0、一時フォルダーのStoreで各条件を1回ずつ測定。実データ・GUIは使っていない。再現: `node scripts/lv4-capacity-runner.mjs`。実測の全値は `capacity-results.json`。本文は同一ASCII文字で構成する合成データであり、ページや履歴の行構成が違えば値は変わる。各ページへの初回本文保存も履歴を1件作る。

| 条件 | checkpoint | 完全バックアップ内DB | hash / 検証 |
|---|---:|---:|---|
| 10ページ、本文各256 B | 8,846 B | 61,440 B | 成功 |
| 100ページ、本文各256 B | 85,528 B | 180,224 B | 成功 |
| 10ページ、本文各8,192 B | 88,206 B | 221,184 B | 成功 |
| 1ページ、本文8,192 B、タイトル20回変更 | 176,631 B | 241,664 B | 成功 |
| 130ページ、本文各8,192 B | 1,142,888 B | 2,281,472 B | 既存の1,048,576 B上限で `payload-too-large` |

ページID等が毎回変わるためバイト数がわずかに変動しうる。バックアップDBはSQLiteのWALを取り込んだ後の大きさ。元DB本体とWALは別々に記録してあり、その単純和を通常時の恒久的な必要容量とはしない。時間は単発で環境依存の参考値であり、性能目標でも保証でもない。

未計測: records、添付、実際のHTTP wire、revisionごとのinbox/outbox、適用前バックアップ累積、通信・適用時間、失敗注入。小・中・大の目標規模や保持方式は未決定。計測により現行の全量checkpointがすべてのworkspaceを扱えるとは言えないため、上限到達時の保全・停止が必要。上限引上げ、履歴削除、差分方式への変更は行っていない。

## 合成revisionの追加計測

DeepSeekが読み取り専用で出力した計測案を親側で確認し、行のソートとSQLiteの文字数ではなくUTF-8バイト数を測る修正を加えて実行した。`node scripts/lv4-capacity-revisions-runner.mjs` で再現でき、詳細は `capacity-revisions-results.json`。同じStoreの実装を使うが、ACKとリモート変更は合成し、HTTPや実サーバーは使っていない。

- 2ページ・短い本文の送信1回ではoutboxのJSON合計3,123 B、20回では145,669 B。各回に履歴も増える条件であり、1 revisionあたり一定量と仮定できない。
- 受信5回のinboxは30,564 B、受信20回では253,458 B。合成の受信ごとにページを追加しており、件数と内容の双方が増えている。
- 1ページの本文を大きくしながら繰り返し保存したケースでは、13回目の送信準備でcheckpoint 1,051,507 Bとなり `invalid-local-workspace-checkpoint` で停止。初回のenable時点で上限を超えた別ケースは `payload-too-large`。

数字はそれぞれ1回の合成実行であり、生成ID、文字列、履歴構成、SQLite状態に依存する。DBファイルやWALのサイズ、送受信エンベロープのJSONバイト数もJSONに記録している。暗黙の古い履歴削除や上限変更はしていない。
