# M1の実行計画：競合データを別の作業領域へ回収して止める

2026-11-08 JST。**実装開始を利用者が明示。M1まで実行中。** 基準は保存済みの `732fad58681c45931c1a16ee90fa1bfcff0a9072`（[Draft PR #7](https://github.com/Hiroto555/Notion_rea/pull/7)）。実装はM1契約・担当カードの範囲に限定し、GUI・実データ操作は開始しない。

M1は **A0：範囲・予算の固定 → A1：通常の適用予約の安全性残件 → A2：保全archiveの一覧・書出し・コピー復元** まで。完成形は「保全した内容を選び、検証して、新しいローカル作業領域として取り出せる」。画面コードは作るが、今回のM1完了は非GUI受入までとする。確認済みLevelはLv3のまま。

詳細なファイル割当・worker指示は [担当カード](M1-DISPATCH-PACK.ja.md)、計画に使った独立レビュー・提案は [計画レビュー記録](M1-PLANNING-REVIEW.ja.md) を参照。

| **Sol XHigh：独立した安全性レビュー** | 契約確定前、保存・復元コア統合後、最終候補の3回をレビュー。問題を再現可能な条件と終了判定へ落とす | 実装担当の自己申告だけで合格にしない |
| **DeepSeek Flash：主な実装担当** | 新規の独立モジュール、UI部品、専用試験、手順書を担当カード単位で実装 | 共通ファイル、API、schema、依存、試験設定を横断変更しない |
| **DeepSeek Pro：難所の担当** | 通常予約journal、新規DBへの内容復元、未解決の難所に限定。Flashと同じ契約・レビューを通す | 同じ機能を複数workerで重複実装しない |
| **DeepSeek：独立試験担当** | 実装者とは別session・別ファイルで、故障・境界・再open・持込み禁止を検証 | 実装の内部値から期待値を自己生成して成功としない |

**12個の担当jobを用意し、最初はDeepSeek 4本、受入実績を見て最大6本へ増やす。** 最大時の目安は実装4本＋独立試験2本。CodexとSolはこの6本に含めず、それぞれの実行枠を確保する。Codex内蔵のsubagent枠とOpenCodeの外部process数は別に管理し、実際の上限に合わせて投入する。枠が空いても依存未成立の仕事は投入しない。

## 2. 実装前に固定する契約（G0）

| 判断 | M1で採る案 | 合格条件・制約 |
|---|---|---|
| 通常適用の予約 | private settings内のUUID付きSQLite journal。pending／cancelled／consumedと対象・結果をstrict canonical JSONで記録 | ID＋期待レコード全体のCAS。通常予約と競合予約の相互排他をreserve／consumeのtransaction内でも確認。消費と本文／applied更新を同一transactionへ入れる |
| 旧sidecar | 存在・破損・差替えは保全してblocked。M1の製品経路は新規作成・自動適用・自動unlinkしない | 旧予約からの自動移行、旧sidecarがある状態での再同意・解除はM1対象外と明示。単なるinode再検査を原子的な解決と扱わない |
| 保全一覧 | mainのローカルarchive service。同期無効・未接続でも使える | 読取りのために同期登録・rebind・schema昇格を行わない。破損1件で他の項目を隠さない。cursorで全件へ到達できる |
| 選択対象 | sourceの識別＋archive ID＋operation ID＋kind＋checkpoint hashを固定したmain所有ticket | picker等のawait後も同じ内容を再検査。rendererから任意pathや書き換えたcheckpointを受け取らない |
| 書出し | ①内容JSONのみ（添付なし・復元可能性未保証）と②検証済み回収bundleを別の結果型にする | ②は必要添付全件のbytes／hash確認が必須。不足時に①を②へ自動格上げしない。通常の完全backup形式を名乗らない |
| コピー復元 | 未使用の新規ディレクトリへ、固定schemaの**user_version=4**のローカルDBを新規構成 | v5のDB／sqlite_master／triggerをコピーしない。内容11表と参照先の添付を回収。既存内容IDは参照維持、新規の復旧用workspace識別はsourceから分離 |
| 持ち込まない情報 | sourceのsettings、同期identity／binding／token、inbox／outbox、通常・競合予約、save receipts、未保存／復旧入力、ローカル成功履歴 | 同期未登録の新規workspace。現在の同期設定で自動起動せず、自動登録・自動送信しない。DB内のページ履歴は内容11表の範囲で保持する |
| 後から起動したときの同期 | destinationに新規生成するprivate settingsの回収由来markerで同期禁止を永続化 | sourceのsettingsをコピーする意味ではない。`FOLIO_SYNC_*`が残る通常起動や手動再接続でも、marker確認を登録・昇格・送信より前に行い保留。破損時も保留。M1に解除操作を追加しない |
| ファイル安全性 | freshな出力、開いたFDのregular-file／size検査、manifestに対するhash、別inodeのコピー、出力再検証、durableな完了marker | symlink・特殊file・意図しないhardlink・path逸脱・検査中の差替えは拒否。失敗した出力は未完了のまま保全し、自動削除しない |

任意の同一UID processによるDB／親path／OS権限の改竄を完全に防御する範囲ではない。A1では、製品の通常writerをSQLite CASへ統一し、既知のread→unlink競合を実行経路から除く。A2では、検査済み内容と実際に出力した内容を照合し、不確実な結果を成功にしない。

## 3. A0で固定する試験規模・資源予算

以下は**M1に提案する試験範囲**であり、製品の推奨規模や実測性能ではない。G0でCodexとSolが境界試験・見積りを照合し、実行に使う値を契約書へ固定する。超過する要件があれば方式変更を追加せず、再見積りで止める。

| 項目 | 固定案 |
|---|---|
| checkpoint | 既存の1,048,576 B上限を維持。本文・DB・履歴を含む全11表が対象。ページ件数だけでは可否を決めない |
| 添付 | 既存の1ファイル20,000,000 Bを維持。M1回収bundleは合計100 MiB／最大1,000ファイルを追加の保守的上限案とする。超過は理由付き保留、上限を黙って上げない |
| 一覧 | 既定50件／page、最大100件。件数・行サイズを検査し、無制限に全JSONを読み込まない |
| 基本fixture | 本文・階層・削除済みページ、旧形式DB、移行済みrecords、履歴、添付を含む小さい合成workspace。別に上限直前／超過／欠損／破損を用意 |
| 容量 | source側・destination側を分けて見積る。既存の容量部品を利用し、追加DB／WAL／添付コピー／検証一時領域と余裕を含める。不明なら出力開始前に保留。実行中のENOSPCも別途試験 |
| メモリ・試験負荷 | 添付はstreamで扱う。workerのVitestは対象ファイルだけ、maxWorkers=1。重いDB／容量試験は同時2本まで |

このA0はM1の実装・試験範囲を固定する作業。Lv4全体の実運用規模、保持・GC・bootstrap・差分転送の設計を終えたとは扱わない。

## 4. 波ごとの投入と統合

| 波 | Codex／Sol | DeepSeekの投入 | 次へ進む条件 |
|---|---|---|---|
| **W0：契約** | Codex C0：入出力・schema・所有表・fault seam・予算を固定。Sol S0：安全性レビュー | D01：規模とfixture提案。D09／D10は試験条件の提案だけ先行可 | G0：P0/P1の契約欠落なし、API・ファイル所有・停止条件が一意 |
| **W1：独立部品** | Codexは共通adapterを用意し、到着順に小さく受入 | D02 journal、D03 catalog、D04 verifier、D05 asset。最初4本。初回2件の受入後、負荷が許せばD09／D10の独立試験を追加 | 各部品の対象試験・差分検査PASS。契約の変更はCodex経由で更新 |
| **W2：回収と復元** | Codex C1：通常予約のtransaction接続、ローカルservice／IPC接続。Sol S1：保存・復元コアをレビュー | D06 export、D07 import、D08 UI部品、継続中のD09／D10、D11復元受入。依存が揃ったjobだけ、上限6本 | G1：通常予約・競合予約が互いを保護。bundle→新規DB再openの同値性と持込み禁止PASS |
| **W3：導線と停止** | Codex C2：App/main接続、全体quiet、候補固定。Sol S2：同じ候補を最終レビュー | D12：回収全経路の独立試験・操作手順。D09〜D11の不具合は元の担当へ限定差戻し | G2：下の終了条件を全て満たし、M1完了を記録して停止 |

統合順は **契約 → journal／catalog／verify／assets → export／import → service／IPC／UI → 独立受入 → 最終候補**。worker間で互いのdirtyツリーを直接参照しない。依存の成果はCodexが受入コミットへ揃えてから渡す。

## 5. DeepSeekを多く使う運転ルール

- **基点と隔離**：実装開始が指示された後に専用M1ブランチを作り、契約コミットからjobごとのworktree／一時データへ分ける。計画文書を含む未コミット差分をHEADだけで取り落とさない。依存更新時はCodexが指定した新基点へ移し、workerが勝手にmergeしない。
- **所有**：1ファイル1担当。共通のStore、sync apply、startup／quit、main IPC、App、shared型、既存backup、package／lockfile／試験設定はCodex。変更が必要なら`CONTRACT_CHANGE`を返し、担当外を編集しない。
- **出力**：job ID、base SHA／tree、編集一覧、差分、契約への対応、実行したコマンド・exit・件数、故障ケース、未確認点、残課題を返す。テスト未実行をPASSにしない。
- **試験の独立性**：実装workerは自分の単体試験、独立workerは別fixtureと故障注入、Codexは統合試験、Solは安全性を確認する。独立試験workerは製品コードを修正せず、最小再現を担当へ返す。
- **投入調整**：初回2件の受入で待機・失敗・統合時間を測る。受入待ちが2件超、重い試験が2本、429が続く、同じAPI差戻しが2件なら新規投入を止め、4本以下へ戻す。並列数は速度保証ではない。
- **jobの上限案**：1jobは主要実装1〜2ファイル＋専用試験、目安600行まで（journal／importは最大900行で個別レビュー）。初回30分で成果／障害を報告、無報告で延長しない。追加修正は2往復まで、それでも未解決ならCodexへ戻す。APIや担当の分割が悪ければ再分割する。
- **総量の上限案**：12job、初回＋修正2回で最大36の実装・修正依頼。別枠の独立レビューを重複実装に使わない。最初の2時間で見積り更新、実行開始から6時間で必ず進捗と残件を再評価。6時間での完了を約束するものではない。
- **モデル資源**：Flashを主力に、ProはD02／D07と難所の上位レビューへ限定。推論量の指定はjobで固定する。暫定上限はDeepSeek合計input 200万token／output 20万token（取得できるusage基準、reasoningの扱いも記録）。上限・取得不能・Go制限に達した場合は新規投入を止める。残予算はCodex統合とSol最終レビューへ先に確保し、追加課金や別契約への切替を自動で行わない。

ローカル確認はOpenCode **1.18.30**、`opencode-go/deepseek-v4.1-flash`／`opencode-go/deepseek-v4-pro` がモデル一覧に存在する。公式はV2へ移行しており、V1の`permission`／`bash`とV2の`permissions`／`shell`は異なる。実行時に権限設定を確認し、広い`--auto`を既定にしない。[公式Permissions](https://opencode.ai/docs/permissions/)。Goには利用枠とExtra Usageの設定があるので、無制限の並列を前提にしない。[公式Go](https://opencode.ai/docs/console/go/)。

## 6. M1の終了条件

全てを**同じ候補commit／tree**の証拠に揃える。PASSと、仕様どおり保全して止まったBLOCKEDを分けて記録する。

| ID | 終了条件 |
|---|---|
| M1-01 | A0のI/O・schema・上限・ファイル所有・試験表を固定し、契約変更の未決事項がない |
| M1-02 | 新しい通常予約がCASで予約／取消し／消費でき、別ID・別対象の誤消去／誤適用がない。正常な通常適用が再openを挟んでも使える |
| M1-03 | 通常・競合の予約がreserve／consume transaction内で互いを拒否。変更・破損・dirty／IME相当の入力・処理中なら保留し、COMMIT応答不明でも二重適用しない |
| M1-04 | 旧sidecarの存在・破損・差替えで旧予約を実行／削除しない。理由付きBLOCKEDを表示でき、未対応の旧予約解除を完了扱いしない |
| M1-05 | 同期無効・未接続でも保全一覧を読め、paginationで古い項目まで到達。1件破損しても正常な項目を回収可能 |
| M1-06 | 選択ticketに固定したarchiveと実際のJSON／bundleが一致。途中で差替え・削除されれば再確認へ戻り、勝手に最新候補へ変更しない |
| M1-07 | JSONだけの書出しと完全な回収bundleを型・表示で区別。添付欠損／hash不一致／上限超過は復元成功にならない |
| M1-08 | 添付全件をmanifestに照合し別inodeへコピー。FD／path差替え・symlink・特殊file・容量不足・途中停止は未完了／結果不明として保全。完了公開やfsyncの応答が不明な場合は、再検証するまで成功にせず、再適用・削除をしない。sourceや既存destinationを削除／上書きしない |
| M1-09 | bundleから新規v4 DBを作り、内容11表・添付・履歴のhash／件数／参照を照合。Store再open後の`buildWorkspaceCheckpoint` hashが選択archiveと一致する。さらに使い捨て復元先で通常保存＋履歴追加を1回行え、再openでも正規に扱える |
| M1-10 | 復元先にsourceの設定／秘密／同期識別／outbox／予約／receipts／未保存入力がない。同期未登録で、元workspaceと混同しない。destination自身の新しい回収由来markerにより、後の通常起動・再接続でも環境変数に関係なく自動登録・送信を保留し、marker破損時も保留する |
| M1-11 | 一覧→選択→検査→書出し→別領域復元→再openをNode／一時SQLiteで通し、原本の内容・archive・添付が不変。保持した未完了出力も成功と誤認しない |
| M1-12 | 型検査、既存＋新規の単体／統合試験、buildがPASS。Sol最終レビューでP0/P1の未解決なし。差戻し後は影響した検査を再実行し、最終全体quietを通す |
| M1-13 | 操作手順・制約・失敗時の保全先・GUI受入待ちを更新。GUI／実IME／物理2台はNOT_RUNのまま。Levelを上げず、A3へ進まずに停止する |

source不変は内容表・archive・添付の論理hashとファイル内容で検証する。稼働中のsource DBについて、正当なWALやcheckpointによる物理配置変化まで「一切のbyte変化なし」と約束しない。新規DB／未完了bundleは完成markerの検査に通るまで通常の復元先として選べない設計とする。

## 7. 停止・再見積りと工数

M1の細分化後の概算は **20〜36人時**。以前の12〜24人時から、通常予約のSQLite化、旧形式の保全停止、新規v4 DBの再構成、独立試験を具体化して更新した。人時はモデルの待ち時間や実際の経過時間とは別で、6並列なら6分の1になるという見積りではない。

| 作業のまとまり | 概算人時（レビュー・試験を含む） |
|---|---:|
| 契約・予算・fixtureの固定 | 2〜3 |
| 通常予約のjournal化と既存経路への接続 | 4〜7 |
| 保全一覧・bundle書出し／検証 | 4〜7 |
| 新規v4 workspaceへの復元 | 4〜7 |
| UI／IPC導線と独立受入 | 4〜8 |
| 最終統合・Solレビュー・引継ぎ | 2〜4 |
| 合計 | **20〜36** |

上限36人時を超える見込み、規模上限の変更、v4再構成の参照整合性を証明できない、既存backup形式の破壊的変更が必要、sourceへの書込みが回収の必須条件となる、予約を保全したまま安全に止められない場合は、新しい実装jobを止め、できた範囲・未達・選択肢を報告する。GUI許可や実機がなければM1の非GUI受入で止める。

**対象外**：添付転送の再開／GC、接続設定・SecretStore製品接続、実server完全backup／restore／epoch、容量方式の大改造、原本へ上書き／既存workspaceへmerge、旧sidecarの自動移行／解除、GUI実行・OS・実機2台、Lv4認定。これらをM1未達の穴埋めとして追加しない。
