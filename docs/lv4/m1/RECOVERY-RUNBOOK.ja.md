# 競合アーカイブ 回収手順書（M1 / D12）

2026-11-08。対象は M1 の非GUI回収導線。状態は **Lv3**。**A3 へは進まず停止**している。
GUI/Electron/ブラウザ/ネイティブダイアログ/OSクリップボードは今回 **NOT_RUN**。以下の手順は
一時DB・一時filesystemだけで検証済みの実装契約に基づく。利用者の実データでは実行しない。

## 0. できること

- 競合アーカイブの一覧と対象の選択
- JSON-only（metadata-only）の退避
- 添付付き回収データ（complete-bundle）の退避
- 回収バンドルからの**新規コピー復元**（元ワークスペースは変更しない）
- 復元結果の再照会（結果不明・未完了の保全先確認）

できないこと、意図的に行わないこと:

- 元ワークスペースへの自動再適用・上書き
- 復元後の自動起動（アプリも同期も起動しない）
- 旧形式の適用予約（sidecar）の解除
- 実データ・master・push/merge・外部ネットワークを使う確認

## 画面での入口（GUI動作は未検証）

1. 「保全した競合データを取り出す」を開き、「最新を読み込む」で一覧を表示する。
2. 日時と保全の種類を確認して「この対象を選択」。JSONだけか、添付付きかを選んで保存先の**親フォルダ**を指定する。実装がその下に新規名のフォルダを作る。
3. 「新規コピーとして復元」は選択archiveから回収バンドルを作り、さらに新しい作業領域へ復元する。親フォルダには回収バンドルと復元先の両方が残る。どちらも自動で開かない。
4. 「直近の結果を再照会」で結果不明を確認する。未確認の出力を削除・自動再実行しない。

既存の保存済みバンドルをファイル選択して復元する画面入口は、このM1では追加していない。独立バンドルの検証・復元は内部APIとNode受入で確認している。以下の詳細は実装・検証担当向けの契約も含む。

## 1. 一覧を確認する

1. 回収パネルまたはIPCで一覧を取得する。既定は50件、最大100件。
2. 続きは返却された `next`（`anchor` と `before`）をそのまま渡す。ページ間でanchorは変えない。
3. 各行の `valid` を確認する。`valid=false` の行は checkpoint が壊れているか上限超過であり、
   対象として選ばない。`reason` と `bytes` だけを記録する。
4. `target` は `source` / `id` / `operationId` / `kind` / `createdAt` / `checkpointHash` の
   すべてが一致した場合だけ採用する。一覧取得後に1つでも変わっていたら選択をやり直す。

一覧・対象読取りは保存済みの同期スコープだけを使う。同期の有効化・再バインド・状態更新・
DDLは呼ばない。同期テーブルが無い場合は空一覧、状態が不正な場合は保留として扱う。

## 2. JSON-only（metadata-only）で退避する

添付を含めず、checkpoint と「復元用ではない」説明だけを新しいディレクトリへ書く。

1. 出力先はワークスペース・既存バンドル・Folioデータ/バックアップの**外**の新規ディレクトリ。
2. 出力前に容量を見積もる。既知payload×4＋64 MiBを満たさない場合は作成しない。
   見積りは予約ではないため、ENOSPCが出た場合は出力を消さず保持する。
3. 完了後、ディレクトリに `FOLIO-RECOVERY-INCOMPLETE` が**無い**ことを確認する。
4. JSON-onlyは復元バンドルではない。`manifest.json` を作らず、添付も含めない。
   このディレクトリをワークスペースとして復元しない。

## 3. 添付付きで回収する（complete-bundle）

1. 手順2と同じ安全な新規出力先を選ぶ。
2. 次が揃うことを確認する。
   - `manifest.json`（`format: folio-conflict-recovery`, `version: 1`）
   - `checkpoint.json`（canonical JSON、1 MiB以内、targetのhashと一致）
   - `assets/<id>`（manifestとcheckpointの全添付。1件20,000,000 B以内）
3. manifestの各 `file` は `assets/<id>` と完全一致し、重複ID・余分なfile・余分なkeyが無いこと。
4. checkpointのworkspace検証とhash/bytes、添付のbytes/sha256を確認する。
   manifestのcanonical SHA256をfingerprintとして保持する。
5. 完了公開の直前に、選択したtargetが変わっていないことを再確認する。
6. `FOLIO-RECOVERY-INCOMPLETE` が消えていること、ディレクトリがfsync済みであることを確認する。
7. 公開応答が不明な場合は「未作成」と判断しない。同じディレクトリを再検証する。

## 4. 新規コピーとして復元する

1. 手順3の回収バンドルを選ぶ。元バンドルの同一／内側、元ワークスペースの内側、
   Folioデータ/バックアップの内側は出力先にできない。
2. 出力先は存在しない新規ディレクトリ。既存ディレクトリは使わない。
3. 次の順で処理する。
   - バンドルを再検証し、fingerprint一致を確認
   - 容量確認（payload×4＋64 MiB）
   - 新規ディレクトリと `FOLIO-RECOVERY-INCOMPLETE` を作成
   - checkpointと全添付をコピー
   - 空の新規Storeへ内容を構築（v4）
   - read-onlyで再openし、hash・回収marker・v4・privateデータ不在を確認
   - 元バンドルを再検証し、fingerprint一致を確認
   - 完了markerを外してfsync
4. 復元先は**新しいUUID**を持つ。内容IDは保持する。元ワークスペースと元バンドルは変更しない。
5. 復元後にアプリを自動起動しない。同期も自動で開始しない。
6. 受入確認では復元先のv4を再openし、checkpoint hashが選択targetと一致することを確認する。
   通常保存と履歴追加は検証用コピーの中だけで行う。

## 5. 復元先へ持ち込まないもの

復元は製品データの11表だけを新しいワークスペースへ構築する。次は持ち込まない。

- 元の設定（`settings`）とUI状態
- 秘密情報・トークン・認証情報・DB dump
- 通常適用の予約（normal apply journal）と競合の選択予約
- `workspace_sync_outbox` / `workspace_sync_inbox` / 同期identity / applied checkpoint
- `save_receipts` と端末固有の受領記録
- 旧形式の適用予約sidecarや端末固有の復旧入力

復元先には回収markerを書き、同期を**保留**にする。後日そのワークスペースを開いても
同期は保留のままで、勝手に送信・適用しない。解除は別作業とし、この手順書では行わない。

## 6. 結果不明（outcome-unknown）の扱い

出力作成後の例外は「未作成」ではない。次を守る。

1. 自動再実行しない。同じIDで新規出力を作らない。同じ出力先へ再適用しない。
2. 削除しない。返却された `directory` と `target` を保全先として記録する。
3. `status(operationId)` で再照会する。
   - 正規の `FOLIO-RECOVERY-INCOMPLETE` がある → `blocked`（未完了として保全）
   - markerが無く、完成検査がすべて通る → 成功へ回収
   - 検査不能（添付欠落・target変更・権限失効など） → `outcome-unknown` のまま
4. 添付欠落で成功へ上がらない場合は、**同じ生成先の同じ添付**を正しいbytes/hashで戻し、
   もう一度 `status(operationId)` で再照合する。新規IDや別出力先へ自動で切り替えない。
5. 未解決のunknownがある間は、新しい操作でその記録を置き換えない。

## 7. 正常な INCOMPLETE の扱い

処理途中で止まり `FOLIO-RECOVERY-INCOMPLETE` が残った出力は**未完了**として扱う。

- 結果は `blocked` と保全先pathになる。削除しない。
- 元ワークスペースと元バンドルは変更しない。
- 必要なら**別の新規出力先**へ新規操作として試行してよい。前の未完了出力は残す。
- INCOMPLETEを手で消して完成扱いにしない。

## 8. 操作IDとセッション

- UIが作る `operationId` は冪等キー。mainが発行する固定target ticketとは別物。
- 同じID・同じtarget・同じmodeの同時retryは**同じPromise**を返し、効果は1回だけ。
- 同じIDでtargetまたはmodeが違う場合は拒否する。
- mainの操作セッションは最大16件。完了済みも削除せず、満杯なら新規IDだけを拒否する。
  既存IDのretryはpickerも出力も増やさない。
- main再起動で操作セッションは失効する。過去の未確認出力は自動再実行せず、
  生成先の手順で再確認する。
- 通常適用・競合選択のSQLite予約は操作セッションとは別で、再起動を越えて保持される。
  混同しない。

## 9. 拒否される条件

次の場合は出力を作らず `blocked` にする。

- 出力先が元ワークスペースの同一／内側
- 出力先が既存の回収バンドル／ワークスペースバックアップの内側
- 出力先がFolioデータ領域の内側
- picker後にtargetが差し替わった
- picker後に権限が失効した
- 容量が不明、または見積りを満たさない
- 同じ操作IDでtarget/modeが変わった
- 直前のunknownが未解決のまま

## 10. 旧sidecar

旧形式の適用予約（sidecar）の解除は**未対応**。検出しても解除・変換・自動適用を試みない。
原本を保全し、この手順書の対象外として報告する。

- 受入: Nodeの一時DB／一時filesystemだけで実施。
- GUI/Electron/ブラウザ/ダイアログ/クリップボード/実データ: **NOT_RUN**。
- 現在の到達点は **Lv3**。**A3は開始しない**。GUI未確認を理由に完成度やLevelを上げない。

  例外）を添えて報告する。
